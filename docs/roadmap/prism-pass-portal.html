Scope, MVP and tracker, built from the repo — not from the docs

Prism Pass already has a working core: tenants, roles, QR passes, a scanner, an offline queue, server-side geofencing, e-signature APIs and DTR exports, all at v0.3.1 in production. What it does not have yet is the event workflow the summit validated: rosters, event close-out, trustworthy offline verification, a name on the scan screen, and certificates. The MVP below is events-first: an organizer runs a real event with no signal at the door and ends with signed certificates. DTR stays as a paid add-on for small companies.

The product decision this plan is built on

At the HR Leaders Innovation Summit the interest came from one feature: scanning that keeps working with no signal. The follow-up discussion settled where Prism Pass should compete. Government agencies already record DTR with biometric terminals, and they will not swap those for a QR code. What biometrics do not cover is everything that happens away from the office door: trainings, seminars, flag ceremonies, off-site events, and the days the biometric terminal is down and staff fall back to a paper logbook.

So the plan treats Prism Pass as an event attendance and certificates platform, sold to organizations first. DTR is kept, but as an add-on for small companies that have no fingerprint scanner, and it is the only place where the heavier anti-cheating controls (selfie plus geofence) apply. Events use the QR plus a staff member looking at the person.

Decision

Why this matters for scope

Most of what is missing is event plumbing, not new technology. The repo can already record a scan, survive offline and sign a document. It cannot yet say "only these 120 people are invited", "this event is closed", or "here is your certificate". Those three gaps are the MVP.

Competitors already offer offline scanning, geofencing and multi-tenancy, so none of those are the selling point on their own. The pitch that holds up is the outcome an HR office actually needs at the end of a training: an attendance record nobody has to encode, and a signed certificate for every attendee, even when the venue had no signal.

Five things to fix before planning anything new

These are ordered by how badly they would hurt a pilot. Each one is verified against the code on develop at commit b902aed.

Critical

1. Offline scans are queued blind

When the scanner is offline it stores the scan and shows "Queued offline — provisional". It never checks the pass on the device, so the staff member at the door cannot tell a valid attendee from a revoked pass, a pass from another organization, or a random QR. The server already builds a pass cache for exactly this (GET /sync-bundle returns pass hashes), but nothing in the scanner downloads or uses it. The feature that won the summit is the one that most needs finishing.

Critical

2. Public production still has password123 demo accounts

admin@syntaxure.dev is an organization Owner and a platform admin, and its password is documented in the README of a public repository. The repo's own known-limitations file says these must be rotated or gated before any real pilot. This is a five-minute fix with a large blast radius if skipped.

High

3. The scanner does not show who was scanned

An accepted scan does not return or display the attendee's name, so staff cannot do the one check that makes a static QR safe: look at the person. Neither the scan route, the scan service nor the scanner page reads the person's display name.

High

4. Any active pass can check into any session

The scan service checks that the pass is valid for the organization and the person is active. It does not check whether that person belongs to that event. Every event in an organization is effectively open to every member. That is fine for an office, wrong for a training with a fixed list of participants.

High

5. Geofencing works on the server but the scanner never sends a location

The scan service evaluates geofences with off, flag and enforce modes, and it was verified live in v0.2.0 with a crafted request. The scanner page never calls the browser location API, so real scans arrive without coordinates and are recorded as NOT_CAPTURED. There is also no screen for drawing a geofence. Per the decision above, this only matters for the DTR add-on, which is why it is not in the event MVP.

Branch and release state

A full clone was used to compare all long-lived branches. The repo retired staging on 9 November: vercel.json now deploys only main (production) and develop. The staging branch still exists, sits at v0.3.0 and is 21 commits behind develop, but nothing deploys from it. lou is fully merged into develop.

main has two commits that develop lacks, but both are a merge and an empty deployment trigger; the content difference is zero. develop is 9 commits ahead with self-serve signup, password recovery, a terms page and an open-redirect fix on login. Those are ready-looking but unreleased. Separately, CHANGELOG.md and package.json say v0.3.1 is in production, but there is no v0.3.1 git tag; the last tag is v0.3.0.

How a scan flows today

The strongest part of the codebase is that online and offline scans share one rule set. Both the live scan route and the batch sync route call performScan in modules/attendance/scan-service.ts, so a scan that syncs later is judged exactly like one recorded live. Offline items are encrypted at rest with a key the browser cannot export, leased so two tabs cannot send the same scan, and signed with a device key so the server can reject replays.

The dashed box is the gap. The server can hand a device everything it needs to verify passes offline, but the scanner skips that step and defers every offline judgement to the server. The result is correct data after sync, but no useful answer at the door while offline.

Scope of work

What we are building, and what we are not

This scope covers the work from today's v0.3.1 to a first real pilot, plus the two follow-on tracks that come after it. It is written so anyone on the team, or an AI agent, can tell whether a piece of work belongs in the current milestone.

Product statement

Prism Pass lets an organization run an event, record who attended even with no signal at the venue, and hand every attendee a signed certificate, without anyone encoding a sign-in sheet.

The first customers are organizations that run recurring trainings and events: agency HR and training units, schools and student councils, and associations. They already own the attendee list and the reason to issue certificates. The scope deliberately does not chase daily office timekeeping, because that market is held by biometric terminals in government and by free apps in the private sector.

Open decisions

These need the product owner's call. Each has a recommendation, but the trade-off is a business one.

Decide before printing IDs

O-1 · Per-organization QR or one global QR for the pilot?

Today each organization issues its own pass. The proposed SSOT moves to one identity QR per person, and plans to stop accepting old passes after a migration window. If the pilot prints hundreds of ID cards with organization passes, moving to global identity later means reprinting them, or keeping the old format alive indefinitely. Recommendation: run the pilot on per-organization passes shown on phones or printed on paper, and do not print durable PVC IDs until O-1 is decided.

Recommendation ready

O-2 · Adopt the RBAC SSOT before or after the pilot?

It is a large migration (new tables, backfill, dual-read, a feature flag) that changes no pilot outcome. Recommendation: after. Ship four role presets on top of the existing seven roles.

Needs input

O-3 · Pilot organization, event and date

The pilot needs a named organization, a real event and a target size. The summit contact is the natural first ask.

Needs input

O-4 · Pricing

D-07 sets the shape. Prices should come from what the pilot organization spends today on sign-in sheets, encoding and certificate printing.

Needs input

O-5 · Is an in-app e-signature enough on certificates?

For certificates of attendance it is likely acceptable. Ask the pilot organization whether their records or audit office needs anything stronger, such as PNPKI.

Assumptions and constraints

  • Stack stays. Next.js 15, Supabase Auth and Postgres with RLS, Prisma, Vercel in syd1. No rewrite.
  • Migrations stay additive and are applied as reviewed SQL files, because prisma migrate hangs on the Supabase pooler.
  • The scanner is a PWA on ordinary Android phones. Anything that needs native capabilities, such as detecting faked GPS, is out of scope.
  • Personal data: attendee names and attendance are personal information under the Data Privacy Act (RA 10173). The pilot needs a privacy notice at registration and a data-sharing understanding with the pilot organization.
  • Offline is bounded. A device can only verify against the data it downloaded. A pass revoked after the download is accepted at the door and caught on sync. This is stated to organizers, not hidden.

Acceptance scenarios

The MVP is accepted when each scenario below passes in a signed-in browser on a phone at 375px, against the deployed develop build, with real data rather than the demo seed. Each is written so a non-developer can run it.

  1. Set up. An organizer creates an event, imports 30 people from a CSV, and adds 25 of them to the roster. Nobody from Syntaxure helps.
  2. Attendee QR. A rostered attendee opens their QR on a phone; another prints theirs on paper. Both scan.
  3. Online door. Staff scan 10 attendees. Each accepted scan shows the attendee's name. A second scan of the same person within the duplicate window is flagged, not double-counted.
  4. Refusals. A person not on the roster, a revoked pass and a pass from another organization are each refused, and the refusal screen shows no name.
  5. No signal. With airplane mode on, staff scan 10 attendees on two phones, including one person on both phones and one revoked pass. The revoked pass is refused on the device. After reconnecting, all valid scans sync and the duplicate person has one record.
  6. Close. The organizer closes the event. The next scan, online or from a device that synced after the close, is refused.
  7. Certificates. Every attendee with a complete record gets a certificate, the signatory signs once for the batch or each certificate per the signing order, and the PDF's QR opens a public verify page that shows the certificate is genuine without exposing other people's data.
  8. Report. The organizer exports the event's attendance as CSV; the numbers match what was scanned.
  9. Isolation. A staff account from another organization cannot see this event, its people or its certificates, by UI or by calling the API directly.

Definition of Done for a work item

A story, fix or task is done only when every line below is true. "Works on my machine" and "the API returns 200" are not on the list. The repo's history shows the gap this closes: features shipped as tested APIs that nobody could use in the app, and screens verified without ever signing in.

  • Acceptance criteria met exactly as written in the item, and shown in a signed-in browser, not only via API.
  • Server-side authorization on every new route through requireOrganizationPermission (or requirePlatformAdmin), RLS still deny-by-default, and denials write an audit row.
  • Tenant isolation covered: a test proves another organization gets 403 or 404.
  • Tests for the domain logic and for allow and deny on each route, added to the suite and passing.
  • CI green on develop: secret scan, typecheck, tests, build.
  • Offline behaviour stated for anything the scanner touches: works offline, or is clearly labelled online-only in the UI.
  • Phone first: checked at 375px and on desktop; keyboard reachable; focus visible; contrast per docs/design/a11y-audit.md.
  • Migrations are additive SQL files, reviewed, applied with the documented method, with a one-line rollback note.
  • Docs updated in the same change: CHANGELOG Unreleased, PLAN.md progress, README status table if a phase changed, known-limitations if a limit was added or removed.
  • No demo shortcuts in production paths: no hard-coded IDs, no seed-only credentials, no secrets in the client bundle.
  • Deployed to the develop environment and smoke-tested there by someone other than the author.

Definition of Done for a release

  • Every item in the release meets the work-item DoD.
  • Version bumped in package.json, CHANGELOG section dated, git tag created on main.
  • develop promoted to main; production GET /api/v1/health reports the new version.
  • Smoke test on production: sign in, open a console, scan one pass online and one offline then sync.
  • Rollback path known: previous Vercel deployment can be promoted, and any migration in the release is additive.

Definition of Ready

Work only starts when it is ready, so that "done" can be checked against something. An item is ready when it has a one-line user story, written acceptance criteria, the permission it needs named, any data-model change identified, and, if it has a screen, a sketch or a reference to an existing screen to copy.
